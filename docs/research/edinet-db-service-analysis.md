# EDINET DB 型サービスの分析と構築設計

対象: https://edinetdb.jp/developers （AI接続型・有価証券報告書データ基盤）
目的: 同種サービスを自前で構築するための、構造分析・技術設計・参入戦略の整理
作成: 2026-08-14

---

## 0. この文書の前提と調査上の制約

**重要**: 本セッションのネットワークポリシーにより `edinetdb.jp` / `edinetdb.com` /
`qiita.com` / `prtimes.jp` への直接アクセスがブロックされている。したがって
以下の「対象サービスの仕様」は、**検索結果のスニペット + 公式EDINET APIに関する
既知の仕様** から再構成したものであり、一次情報での検証はできていない。

数値・エンドポイント名・料金は **要一次検証** として扱うこと。
特に指標数・社数・ツール数は公開時期によって変動している（後述 §1.3）。

一方、**「公式EDINET APIの制約」「XBRL正規化の困難さ」「アーキテクチャ設計」
「法務論点」「参入戦略」** の各節は一次情報への依存が小さく、そのまま実装判断に
使える精度で書いている。

## 1. 対象サービスの構造分析

### 1.1 サービスの本質

EDINET DB は一言でいえば **「金融庁EDINETの生XBRLを、名寄せ済みの構造化データに
変換して、REST APIとリモートMCPで配信するサービス」** である。

```
金融庁 EDINET (生XBRL/CSV)          ← 無料・公開・機械可読だが「書類」単位
        │
        │  ★ ここが全付加価値
        │  ・書類 → ファクト への分解
        │  ・会計基準×企業ごとに違う要素IDの名寄せ
        │  ・企業マスタの同定（EDINETコード ↔ 証券コード ↔ 名称変更履歴）
        ▼
EDINET DB (正規化済みDB)
        │
        ├─ Web（企業ページ・無料・登録不要） → SEO集客エンジン
        ├─ REST API（APIキー・従量プラン）  → 開発者向け
        └─ リモート MCP                     → ★ 本命の差別化
                └─ Claude.ai / ChatGPT / Cursor / Cline から直接接続
```

運営は Cabocia株式会社。β公開から約10日で API利用登録1,300件超という数字を
プレスリリースで出しており、**開発者獲得のスピードが初期KPI**に置かれている。

### 1.2 プロダクトの三層構造（ここが設計の妙）

| 層 | 課金 | 役割 | 意図 |
|---|---|---|---|
| Web企業ページ | 無料・登録不要 | 4,000社×数ページ = 数千〜万ページ | **SEOで検索流入を取る**。「〇〇 有価証券報告書」「〇〇 財務」等のロングテール |
| ブログ/ドキュメント | 無料 | 「EDINET APIとは」「MCPサーバーとは」等の解説記事群 | 技術検索からの上流獲得。自社をリファレンス化 |
| API / MCP | Free→有料 | 実データ配信 | 収益化ポイント |

**Webとブログを完全無料・無登録にしてSEO資産化し、APIで課金する**という構造。
検索結果でも `edinetdb.jp/blog/*` が広範なクエリで上位に出ており、
コンテンツSEOが実際に機能している。後発が最も苦戦するのはここ。

### 1.3 公開されているスペック（数値は変動あり・要検証）

| 項目 | 値 | 出典の性質 |
|---|---|---|
| 対象企業数 | β時 3,848社 → 3,832社 → 約4,400社 → 4,645社 | 公開時期で増加。上場企業のみ→提出会社全体へ拡張したと推測 |
| 財務指標数 | 69指標（β時はごく基本のみ） | プレスリリース系 |
| 標準フィールド数 | 151〜152項目 | 技術記事系 |
| 対応会計基準 | 日本基準 / IFRS / 米国基準 の3種 | 技術記事系 |
| 名寄せ対象要素ID | 170〜200+パターン | 技術記事系 |
| カバレッジ | 約99.6% | 自社公表値 |
| APIエンドポイント数 | β時11本 → 現在74本 | 大幅拡張 |
| MCPツール数 | 69ツール | 要検証（§4で論点化） |
| データソース | EDINET（有報等）+ TDnet（決算短信・適時開示3分類） | `get_financials` / `get_earnings` で分離提供 |

**料金プラン**（launch時に恒久50%オフキャンペーンあり = 括弧内）

| プラン | 月額 | 日次上限 |
|---|---|---|
| Free | ¥0 | 100回/日 |
| Pro | ¥4,980（¥2,490） | 1,000回/日 |
| Business | ¥29,800（¥14,900） | 10,000回/日 |
| Enterprise | 個別見積 | — |

- レート制限は**日次カウンタ + JST基準リセット**（月次枠は毎月1日リセット、
  ローリング30日ではない）
- Web閲覧は無料・登録不要。課金対象はAPI/MCPのみ
- 商用利用は全プランで可。**データの再配布とAPI再提供のみ禁止**

### 1.4 機能面の差別化ポイント（対象サービスが自ら訴求している点）

1. **リモートMCPネイティブ** — 「サイトを後からMCP化した」のではなく
   「最初からデータ自体がMCPサーバー」という設計思想を明言している
2. **名寄せロジックの公開** — ブラックボックスにせず2層方式を記事で開示。
   財務データで最も重要な「信頼」を、透明性で獲得する戦略
3. **AI総合意見 / 財務健全性スコア（ロジック公開）**
4. **有報の本文テキストも提供**（数値だけでない）

## 2. なぜこのサービスに価値があるのか（= 解いている痛み）

公式EDINET APIは**無料**で誰でも使える。にもかかわらず有料サービスが成立する
理由を正確に理解しないと、作るものがズレる。

### 2.1 公式EDINET API v2 の実像

```
GET https://api.edinet-fsa.go.jp/api/v2/documents.json
      ?date=2026-06-27&type=2&Subscription-Key=<APIキー>
      → その日に提出された「書類のメタデータ一覧」

GET https://api.edinet-fsa.go.jp/api/v2/documents/{docID}
      ?type=1&Subscription-Key=<APIキー>
      → type=1: XBRL一式(ZIP) / 2: PDF / 3: 代替書面 / 4: 英文 / 5: CSV
```

つまり公式APIは **「書類の配達API」であって、データベースではない**。

決定的な制約:

- **日付でしか引けない。** 「トヨタの過去10年の売上」を取るには、
  過去10年分の日次一覧を全部叩いて（≒3,650リクエスト）目的のdocIDを見つけ、
  ZIPを落として中のXBRLを解析する必要がある
- **銘柄コード横断の検索がない。** 「営業利益率20%超の企業」のようなクエリは不可能
- **時系列がない。** 各書類は独立。期間比較は自前で組み立てる
- 遡れる期間には上限がある（直近10年程度／**要仕様書確認**）
- 取得できる形式が生XBRL。**2024年4月からCSV(type=5)も提供**され楽になったが、
  それでも「書類内のCSV」であり横断DBではない

### 2.2 XBRL構造化の4大難所（ここが参入障壁の本体）

#### (1) 会計基準ごとに要素IDが違う

同じ「売上高」が、

- 日本基準: `jppfs_cor:NetSales` / `jppfs_cor:OperatingRevenue1` / `jppfs_cor:SalesOfServices`…
- IFRS: `jpigp_cor:RevenueIFRS` / `jpigp_cor:NetSalesIFRS`…
- 米国基準: また別
- **企業独自拡張**: `E01234-000:重要な売上区分` のように、企業ごとのprefixで
  勝手に定義される（IFRS採用企業で特に多い）

対象サービスが「2層方式（Layer1=標準マッピング170+パターン、
Layer2=正規表現フォールバック）」を採っているのは、
**Layer1だけでは企業独自拡張IDを拾えず、カバレッジが伸びない**からである。
99.6%という数字は、この泥臭いフォールバックの成果物。

#### (2) コンテキストの選別

XBRLの各値には context が紐づく。

- 期間: 当期 / 前期 / 前々期（`CurrentYearDuration`, `Prior1YearDuration`…）
- 連結 / 個別（`NonConsolidatedMember`）
- 時点 / 期間（BSは時点、PLは期間）
- 予想値・非財務セグメント等のメンバー軸

**「当期・連結・実績」の1つを正しく選ぶ**ロジックが必要で、ここを間違えると
静かに嘘の数字が出る。財務データサービスで最も怖い故障モード。

#### (3) 単位・符号・スケール

- 単位: 円 / 千円 / 百万円（`decimals`, `unitRef`）
- 符号: 費用・損失を正で書くか負で書くかが要素により異なる（`balance`属性）
- パーセント・株数・人数の混在

#### (4) 書類の版管理と制度変更

- **訂正報告書**（訂正有価証券報告書）で数値が後から変わる
  → 「提出時点の値(as-reported)」と「訂正後の値(restated)」のどちらを返すのか
- 決算期変更（12月期→3月期等）による変則決算期間
- 会計基準の途中変更（日本基準→IFRS）で時系列が非連続になる
- **2024年4月から四半期報告書制度が廃止**され半期報告書に一本化。
  四半期の数値は EDINET では取れず **TDnetの決算短信**が必要になった
  → 対象サービスがTDnet対応（`get_earnings`）を追加したのはこの制度変更が理由

主要 docTypeCode（抜粋・要コード表確認）:
`120` 有価証券報告書 / `130` 訂正有価証券報告書 / `140` 四半期報告書（廃止済）/
`160` 半期報告書 / `180` 臨時報告書

### 2.3 結論：売っているものは「データ」ではなく

| 顧客が払う対価 | 内容 |
|---|---|
| **時間** | 上記(1)〜(4)を自前で作れば、まともな精度に到達するまで数ヶ月 |
| **正確性の保証** | 「静かに間違った数字」を踏まないこと |
| **監査可能性** | その数字がどの書類のどの要素から来たか追えること |
| **AIからの到達性** | MCPで会話から直接引ける（ブラウザもコードも不要） |

無料の公式APIが存在する市場で課金するには、**この4つを常に説明できる**必要がある。

## 3. 自前で作る場合のアーキテクチャ設計

### 3.1 全体構成

```
[1] Ingestion         日次バッチ + 初回バックフィル
      EDINET /documents.json を日付走査 → docID発見 → ZIP/CSV/PDF取得
      TDnet 決算短信 も別系統で取得
        │
        ▼
[2] Raw Data Lake     S3 / Cloudflare R2 に生ファイルを不変保存
      ★最重要: 正規化ロジックは必ず何度も変わる。生データを持っていれば
        全期間を再パースできる。持っていないと死ぬ
        │
        ▼
[3] Normalization      2層方式
      Layer1: 会計基準 × 指標 の標準要素IDマッピング表（YAML/DBで管理）
      Layer2: 正規表現フォールバック（企業独自拡張ID対応）
      + コンテキスト選別 + 単位正規化 + 符号正規化
        │
        ▼
[4] Storage (Postgres)
      companies : edinet_code(PK), sec_code, 名称, 名称履歴, 業種, 会計基準
      documents : doc_id(PK), edinet_code, doc_type, period_start/end,
                  submitted_at, is_amendment, amends_doc_id, raw_object_key
      facts     : company_id, fiscal_year, period_type, consolidated(bool),
                  field_key, value numeric, unit, ★source_element_id,
                  ★source_doc_id, as_of
      metrics_mv: 69指標の横持ちマテビュー（API配信用）
        │
        ▼
[5] Serving
      REST API (OpenAPI駆動)  ┐
      Remote MCP (Streamable HTTP) ├─ 同一のクエリ層を共有
      Web (SSG/ISR・SEO用)     ┘
        │
        ▼
[6] Auth / Metering / Billing
      APIキー → Redis日次カウンタ（JST 0時リセット）→ Stripe
```

### 3.2 設計上の非交渉ポイント

**(a) 生データレイクは必須。** 正規化ロジックのバグ修正・指標追加のたびに
全期間を再構築する。EDINETを再度全部叩き直すのは非現実的（かつ相手に失礼）。

**(b) すべてのファクトに出所を持たせる。**
`facts.source_element_id` と `facts.source_doc_id` は削らない。
これは監査可能性であり、同時に**デバッグ手段**であり、**競合差別化**でもある。
「この売上高はどこから？」に即答できるサービスは信頼される。

**(c) 冪等な取り込み。** 同じ日付を何度流しても結果が変わらないこと。
訂正報告書は「上書き」ではなく**追加**し、ビュー側で最新版を選ぶ
（as-reported を失わないため）。

**(d) 名寄せ表をコードに埋めない。** マッピング表はデータとして持ち、
バージョンを付ける。EDINETタクソノミは毎年改訂される。

### 3.3 データ規模の見積り

| 項目 | 概算 |
|---|---|
| 対象書類数 | 約4,000社 × 10年 × （有報1 + 半期/四半期3 + 訂正等） ≒ 15万〜20万書類 |
| 生データ容量 | XBRL ZIP 平均2〜5MB → **300GB〜1TB**（PDFも保存するなら増える） |
| facts行数 | 4,000社 × 10年 × 150項目 × 2(連結/個別) ≒ **1,200万行** |
| 月額インフラ | オブジェクトストレージ数千円 + Postgres小〜中規模 + アプリ = **月1〜3万円**規模で成立 |

**インフラは安い。高いのは §2.2 の名寄せを詰める人的コスト。**
参入障壁は技術ではなく根気にある。

### 3.4 初回バックフィルの実務

- 過去10年分 = 約3,650回の `/documents.json` 呼び出し + 書類本体DL
- **必ずレート制御して数日かけて流す**（並列度を絞る・夜間に回す）。
  公的インフラに負荷をかけるとアクセス制限を受け、事業の根が絶たれる
- CSV(type=5)が使える書類は先にCSVで最短の価値（10〜20指標）を出し、
  XBRL精査は後追いでよい

## 4. MCP設計（後発が最も差をつけられる場所）

### 4.1 「1エンドポイント = 1ツール」にしてはいけない

対象サービスは REST 74本 / MCP 69ツールを掲げている。ツール数は営業上の
訴求力になるが、**MCPクライアント側では全ツール定義がコンテキストを消費する**。
69ツールはClaude/ChatGPTのコンテキストを相当量圧迫し、
AIのツール選択精度も落ちる。

後発の勝ち筋は逆張りで、**少数の高機能ツール**に寄せること。

```
search_companies(query, filters)      企業を探す（名称/コード/業種/規模）
get_company(code)                     企業の基本情報と利用可能期間
get_financials(codes[], fields[], periods[], basis)
                                      ★複数社・複数指標・複数期を1回で
compare(codes[], fields[], period)    横断比較（ランキング/スクリーニング）
get_disclosure_text(code, section)    有報テキスト（リスク/MD&A/セグメント等）
get_source(fact_id)                   出所（docID・要素ID・原本リンク）
```

`get_financials` を**バッチ対応**にするのが要点。1社1指標1期ずつ呼ばせると
AIが数十回ツールコールし、レート制限に当たり、遅い。
「10社 × 5指標 × 5期を1コール」で返せる設計にすれば、
Free枠100回/日でも実用的な分析が回る。**これはUXであり、コスト構造でもある。**

### 4.2 レスポンス形式はトークン効率で選ぶ

LLMに数値表を渡すとき、冗長なJSONは不利。

```
悪い: [{"company":"トヨタ自動車","fiscal_year":2025,"field":"net_sales","value":45095325000000,"unit":"JPY"}, ...]
良い: code,year,net_sales,operating_income,net_income   ← ヘッダ1行 + 密なCSV
      7203,2025,45095325,5352934,4765086
      (unit: 百万円 / 連結 / 日本基準 は1回だけ宣言)
```

同じ情報量でトークンが3〜5分の1になる。MCPは**返却フォーマットの設計自由度**が
高いので、ここは必ず最適化する。

### 4.3 AIの誤読を防ぐ責務はサーバー側にある

財務データでAIが最も間違えるのは以下。**レスポンスに必ず明示する。**

- 単位（円 / 千円 / 百万円）
- 連結 / 単体
- 会計基準（日本基準 / IFRS / 米国基準）
- 実績 / 予想
- 会計期間（変則決算・決算期変更の注記）
- **訂正の有無**

ツールのdescriptionにも「値は百万円単位・連結・実績」等を書き、
LLMが単位を取り違えたまま比率計算しない設計にする。
ここを曖昧にすると「AIが自信満々に間違う」最悪のUXになる。

### 4.4 接続方式

- **Remote MCP（Streamable HTTP）**が本命。Claude.ai / ChatGPT / Cursor /
  Cline のコネクタとして登録できる形にする
- 認証: APIキーヘッダで始め、需要が出たらOAuth 2.1へ
- ローカルstdio版も配布すると開発者の初速が上がる（npx一発）

## 5. 法務・コンプライアンス論点

| 論点 | 内容 | 対応 |
|---|---|---|
| **元データの権利** | EDINET開示書類は金融庁の電子開示システム経由の公開情報。EDINET利用規約 / API利用規約に従う | 出典表示、加工物である旨の明示、免責。**規約原文を必ず読む** |
| **金融商品取引法（投資助言・代理業）** | 「AI総合意見」「スコア」が個別銘柄の**売買推奨**に読めると投資助言業に該当しうる | 事実の要約と定量スコアに限定。売買推奨・目標株価を出さない。免責を明記。**要法務確認** |
| **データの正確性** | 誤った財務データによる損害 | 利用規約で保証否認 + 出所リンクで検証可能に |
| **自社データの再配布** | 対象サービスは「再配布・API再提供の禁止」で自衛している | 同様の条項。ただし商用利用は広く許可する方が普及する |
| **TDnet/決算短信** | 各社IRページ・TDnetの利用条件はEDINETと別 | 個別に確認。スクレイピングの可否・負荷に注意 |
| **特商法・資金決済** | サブスク課金 | Stripe + 特商法表記 |

**「AI総合意見」を出すなら金商法の確認は先にやること。** 後から機能を削るのは
プロダクト上の痛みが大きい。

## 6. 競合マップと自分の置き場所

| 競合 | 強み | 弱み |
|---|---|---|
| **公式EDINET API**（金融庁） | 無料・一次情報・全書類 | 書類配達のみ。横断検索・時系列・名寄せなし |
| **EDINET DB**（今回の対象） | MCPネイティブ、名寄せ公開、安価、SEO強い、TDnet対応済 | 先行だが単一データソース系。まだ若い |
| **J-Quants API**（JPX系） | 株価・売買情報の一次性。公式 | 有報テキスト・詳細財務は薄い |
| **バフェット・コード等** | 個人投資家向けUI、指標が豊富 | API/AI接続は主眼でない |
| **SPEEDA / QUICK / 日経NEEDS** | 網羅性・品質・サポート | 年数百万円級。個人・小規模開発者には届かない |
| **スクレイピング系（Yahoo/株探）** | 手軽 | 規約リスク・不安定 |

**空いている席**: 「機関投資家向け高額サービス」と「無料の生API」の間の
**AIネイティブ・監査可能・月数千円**というレンジ。ここに対象サービスが座った。
後発は同じ席を奪うのではなく、**隣に座る**ほうが合理的（§7）。

---

## 7. 後発として何で勝つか（差別化候補）

対象サービスは既にTDnet決算短信まで対応済みで、「速報性の欠落」という
分かりやすい穴は埋まっている。残る有効な差分は以下。

### 優先度高

1. **訂正・修正再表示（restatement）の完全追跡**
   as-reported と restated を両方持ち、差分を返す。
   「いつ何がどう訂正されたか」はプロが確実に金を払う情報で、
   実装が地味に重いため参入されにくい。§3.2(c)の設計がそのまま効く。

2. **有報テキストの構造化 + セマンティック検索**
   数値は誰でも整備する。差がつくのは本文側。
   事業等のリスク / MD&A / セグメント情報 / 政策保有株式 / 役員報酬 /
   従業員数・平均年収 / 大株主 を**項目単位で構造化**し、埋め込み検索を付ける。
   「政策保有株式を3年で半減させた企業」のようなクエリは既存サービスで難しい。

3. **監査可能性を一級市民に**
   全ファクトに「原本PDFの該当ページへのディープリンク + 要素ID」を付ける。
   AI回答に必ず出所が付く = 実務で使える。信頼が最大の非機能要件。

### 優先度中

4. **株価との結合**（J-Quants等と接続）でPER/PBR/EV/EBITDA等のバリュエーションを提供。
   有報単体では出せない指標が一気に増える。
5. **英語対応**。海外機関投資家・海外ヘッジファンドは単価が桁違い。
   EDINETの英文書類(type=4)は限定的なので、日→英の指標名・注記の翻訳品質が武器になる。
6. **バーティカル特化**。M&A候補スクリーニング、与信審査、就活・採用（平均年収・
   従業員数・離職）、ESG。汎用APIより高い単価が取れる。

### やらないほうがよいこと

- **指標数・ツール数での勝負**（69 vs 100の競争は消耗戦、かつ§4.1のとおり
  ツール数は多いほど良いわけではない）
- **料金の単純な下回り**（インフラが安い市場では価格競争が底なしになる）

## 8. 段階的実装計画

| Phase | 期間目安 | 内容 | 完了条件 |
|---|---|---|---|
| **0. 基盤** | 1〜2週 | EDINET APIキー取得、日次取り込み、生データレイク、過去分バックフィル開始 | 任意日の書類一覧と本体が冪等に取れる |
| **1. 最短の価値** | 1〜2週 | CSV(type=5)ベースで主要10〜20指標、企業マスタ、Postgres投入 | 「1社の売上/営業利益/純利益の過去5年」がSQLで引ける |
| **2. 正規化本番** | 3〜6週 | 2層名寄せ（Layer1マッピング表 + Layer2正規表現）、コンテキスト選別、単位・符号、**出所記録** | 主要指標のカバレッジ95%超 + 全値に出所が付く |
| **3. REST API** | 1〜2週 | OpenAPI定義 → 6〜10エンドポイント、APIキー、日次レート制限 | Free枠で外部開発者が使える |
| **4. MCP** | 1〜2週 | Remote MCP（§4のバッチ型・少数ツール設計） | Claude.ai / ChatGPT に接続して会話から分析できる |
| **5. Web/SEO** | 2〜4週 | 企業ページのSSG/ISR（数千ページ）+ 解説記事 | 検索流入が発生し始める |
| **6. 収益化** | 1〜2週 | Stripe、プラン、使用量ダッシュボード | 課金が回る |
| **7. 差別化** | 継続 | §7の1〜3（訂正追跡・テキスト構造化・監査リンク） | 対象サービスにない価値が出る |

**Phase 2 が全体の山**であり、ここを軽く見積もると必ず破綻する。
「動くもの」は2週で出るが、「信用できるもの」は数ヶ月かかる。

MVPとして最短で外に出すなら **Phase 0→1→4（MCPを先、RESTを後）**もあり得る。
AI経由の体験がこのプロダクトの主張なので、デモの威力が最も高い。

## 9. リスク

| リスク | 影響 | 緩和 |
|---|---|---|
| **EDINETタクソノミの年次改訂** | 名寄せ表が毎年壊れる | マッピングをデータ化・バージョン管理。カバレッジ低下の自動検知アラート |
| **単一データソース依存** | EDINET仕様変更・停止で事業停止 | 生データレイクを自前で持つ（過去分は生き残る）+ TDnet等の複線化 |
| **静かな数値誤り** | 信頼の一撃喪失 | 出所記録 + 既知企業のゴールデンデータでの回帰テスト（CIで数十社を毎日検証） |
| **先行者のSEO/登録者優位** | 集客が伸びない | 正面衝突を避け §7 のニッチから入る。技術記事は「対象サービスにない話題」で書く |
| **「無料の公式APIがあるのに払う理由」** | 転換率が上がらない | §2.3 の4つ（時間・正確性・監査可能性・AI到達性）を常にLPで説明 |
| **金商法（投資助言）** | サービス停止リスク | AI意見の出し方を事前に法務確認 |
| **公的インフラへの過負荷** | アクセス制限 | 取り込みのレート制御を絶対に守る |

## 10. 結論（実装判断）

- **技術的には十分に作れる。** インフラ規模も小さく、月数万円で運用できる。
- **難所は1つに集約される**: XBRLの名寄せ（会計基準差・企業独自拡張・
  コンテキスト選別・訂正管理）。ここが参入障壁で、対象サービスの実質的な資産。
- **設計上の一級要件は「出所の記録」と「生データレイク」。**
  この2つを最初から入れておけば、後からいくらでもやり直せる。入れないと詰む。
- **正面から同じものを作るのは推奨しない。** 対象サービスは既にMCP・TDnet・
  SEO資産を持っている。勝ち筋は §7 の「訂正追跡」「有報テキストの構造化検索」
  「監査可能性の徹底」のいずれかを軸にした隣接ポジション。
- **MCP設計は後発の明確な優位点になりうる**（§4.1のバッチ型・少数ツール、
  §4.2のトークン効率、§4.3の単位明示）。ツール数の多さは強みではない。

### 次に決める必要があること

1. ターゲット顧客（個人開発者 / 機関投資家 / 事業会社の企画部門 / 海外）
2. §7 のどの差別化軸を主軸にするか
3. 「AI総合意見」相当を出すか（出すなら法務確認を先に）
4. 技術スタック（言語・DB・ホスティング）
