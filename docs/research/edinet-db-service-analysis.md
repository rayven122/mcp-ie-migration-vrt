## 2. 対象サービスの設計判断で「効いている」点

競合分析として最も重要なのは、機能一覧ではなく**なぜその設計を選んだか**である。
以下4点は明確に思想があり、後発が真似する価値がある。

### 2.1 過去上場826社を含める = サーバイバル・バイアス対策 ★

現役3,820社だけでなく、**MBO・合併・経営統合で上場廃止になった826社**を保持している。

これは単なる網羅性の話ではない。**生存企業のみのデータで統計を取ると結果が systematically
歪む**（生き残った企業だけを見れば収益性は過大評価される）。学術研究・バックテストでは
致命的な欠陥になる。

そして実際に「東京大学・京都大学・一橋大学・慶應義塾大学・早稲田大学、ミシガン大学・
ザンクトガレン大学・ノースイースタン大学、米連邦政府の政策研究者」に使われている [確]。
**過去上場を入れたからこそ学術利用が取れている**という因果だと読める。

学術リファレンス化は、論文に引用されるほど参照が積み上がる**複利型の堀**である。
機能で追い抜いても、この堀は埋まらない。

### 2.2 「ハルシネーションしない構造」を構造で保証 ★

- XBRLを**決定論的に**パース。**LLMは数値抽出・名寄せ・集計に介在しない** [確]
- 1データ点ごとに `docID` を保持し、EDINET原本PDFに1クリックで到達 [確]
- AI分析・財務健全性スコアは**ルールベース**。判定ロジックを全公開し、
  同一入力から常に同一スコアが再現される [確]

「AI分析」を謳いながら**数値生成にLLMを使わない**のは正しい設計判断である。
LLMを名寄せに使うと、静かに間違った数字が混入し、再現性が失われる。
再現性の欠如は学術利用と法人利用の両方で失格条件になる。

### 2.3 金商法リスクを設計で回避

「本サイトのデータは情報提供のみを目的としており、**投資助言・代理業に該当するものでは
ありません**」を明記 [確]。加えて、

- スコアはルールベース + ロジック公開 = 裁量的な推奨ではなく機械的な計算
- 個別銘柄の売買推奨・目標株価を出していない

**「AI総合意見」を出しつつ投資助言業に触れない**ための組み立てとして参考になる。

### 2.4 流通経路への投資

- **Google「優先ソースに登録」への誘導** [確] — トップニュース枠での優先表示を狙う
- Claude.ai / ChatGPT / Copilot Studio ごとの接続ガイド
- プレスキット、発行体（IR・広報）向け窓口

データを作るだけでなく、**AI・検索の両方の流通経路を押さえる**動きをしている。

## 3. 本当の競合構造：単一サービスではなくプラットフォーム ★

ここが参入判断で最も重要な発見である。フッターに以下が並んでいる [確]。

```
「日本の一次情報インフラ」
  AIが断言する前に、裏が取れる。日本の一次情報をドメイン横断で構造化するデータ基盤群

  EDINET DB   金融（有価証券報告書）
  SEISAKU DB  政策・公的支出データ
  不動産DB     不動産・地価データ
  BOUSAI DB   災害リスク・ハザード
  まちずかん    全国市区町村の不動産カルテ
```

つまり **EDINET DB は5つのうちの1つ**であり、事業の本体は
「**日本の公的一次情報を、AIが検証可能な形に構造化する基盤群**」である。

参入判断に直結する含意:

1. **コスト構造で不利になる。** 取り込みパイプライン・名寄せ基盤・API/MCP層・課金・
   SEOテンプレートを5ドメインで償却している相手に対し、1ドメイン専業で挑むことになる
2. **EDINET単体で勝っても勝ちにならない。** 相手の勝ち筋は「AIが日本の一次情報を
   引くときの既定の接続先」になること。金融だけ取っても包囲される
3. **同じプレイブックは他ドメインで再現できる。** 彼ら自身がそれを証明している。
   未着手ドメイン（医療・特許・司法・教育・農林水産・交通・統計）は空いている

## 4. なぜこの領域に価値があるのか（技術的な参入障壁）

公式EDINET APIは**無料**である。それでも有料サービスが成立する理由。

### 4.1 公式EDINET API v2 の実像

```
GET https://api.edinet-fsa.go.jp/api/v2/documents.json?date=YYYY-MM-DD&type=2&Subscription-Key=<key>
    → その日に提出された「書類のメタデータ一覧」

GET https://api.edinet-fsa.go.jp/api/v2/documents/{docID}?type=1&Subscription-Key=<key>
    → type=1:XBRL(ZIP) / 2:PDF / 3:代替書面 / 4:英文 / 5:CSV
```

公式APIは **「書類の配達API」であってデータベースではない**。

- **日付でしか引けない。** 「トヨタの過去10年の売上」には過去10年分の日次一覧
  （≒3,650リクエスト）を走査し、ZIPを落として解析する必要がある
- **銘柄コード横断の検索がない。** 「営業利益率20%超」のようなクエリは不可能
- **時系列がない。** 各書類は独立
- 遡及可能期間に上限あり（直近10年程度 / [要検証]）
- 2024年4月からCSV(type=5)提供で改善したが、それでも「書類内のCSV」

### 4.2 XBRL構造化の4大難所（= 参入障壁の本体）

#### (1) 会計基準ごとに要素IDが違う

同じ「売上高」が、

- 日本基準: `jppfs_cor:NetSales` / `OperatingRevenue1` / `SalesOfServices`…
- IFRS: `jpigp_cor:RevenueIFRS` / `NetSalesIFRS`…
- 米国基準: さらに別系統
- **企業独自拡張**: `E01234-000:...` のように企業ごとのprefixで勝手に定義される
  （IFRS採用企業で特に多い）

2層方式（Layer1: 標準要素IDマッピング / Layer2: 正規表現フォールバック）が必要になるのは、
**Layer1だけでは企業独自拡張IDを拾えずカバレッジが伸びない**ため。

#### (2) コンテキストの選別

各値に context が紐づく。期間（当期/前期/前々期）、連結/個別、時点/期間（BSは時点・PLは期間）、
予想値、セグメント軸。**「当期・連結・実績」を正しく1つ選ぶ**ロジックが必要で、
ここを誤ると静かに嘘の数字が出る。財務データサービスで最悪の故障モード。

#### (3) 単位・符号・スケール

円/千円/百万円（`decimals`, `unitRef`）、費用・損失の符号（`balance`属性）、
パーセント・株数・人数の混在。

#### (4) 版管理と制度変更

- **訂正報告書**で数値が後から変わる → as-reported と restated のどちらを返すか
- 決算期変更による変則決算期間、会計基準変更（日本基準→IFRS）による時系列非連続
- **2024年4月に四半期報告書制度が廃止**され半期報告書に一本化。
  四半期数値はEDINETでは取れず、TDnetの決算短信が必要

主要 docTypeCode（[要検証: コード表確認]）:
`120` 有価証券報告書 / `130` 訂正有価証券報告書 / `140` 四半期報告書（廃止）/
`160` 半期報告書 / `180` 臨時報告書

### 4.3 顧客が払う対価

| 対価 | 内容 |
|---|---|
| **時間** | 上記(1)〜(4)を自前で作り、実用精度に達するまで数ヶ月 |
| **正確性** | 「静かに間違った数字」を踏まないこと |
| **監査可能性** | どの書類のどの要素から来たか追えること |
| **AI到達性** | MCPで会話から直接引ける |

**インフラは安い。高いのは名寄せを詰める人的コスト。参入障壁は技術ではなく根気にある。**

## 5. 自前で作る場合のアーキテクチャ

### 5.1 全体構成

```
[1] Ingestion       日次バッチ + 初回バックフィル
      EDINET /documents.json 日付走査 → docID → ZIP/CSV/PDF 取得
      TDnet 決算短信は別系統
        ▼
[2] Raw Data Lake   S3 / R2 に生ファイルを不変保存
      ★正規化ロジックは必ず何度も変わる。生データがあれば全期間を再パースできる
        ▼
[3] Normalization   Layer1: 会計基準×指標の標準要素IDマッピング（データとして管理）
                    Layer2: 正規表現フォールバック（企業独自拡張ID）
                    + コンテキスト選別 + 単位/符号正規化
        ▼
[4] Storage (Postgres)
      companies : edinet_code(PK), sec_code, 名称, 名称履歴, 業種, 会計基準,
                  listing_status, delisted_at, delisting_reason  ← ★過去上場を保持
      documents : doc_id(PK), edinet_code, doc_type, period_start/end,
                  submitted_at, is_amendment, amends_doc_id, raw_object_key
      facts     : company_id, fiscal_year, period_type, consolidated,
                  field_key, value numeric, unit,
                  ★source_element_id, ★source_doc_id, ★first_reported_at
      metrics_mv: 指標横持ちマテビュー（API配信用）
        ▼
[5] Serving   REST（OpenAPI駆動）/ Remote MCP / Web(SSG/ISR) が同一クエリ層を共有
        ▼
[6] Auth / Metering / Billing   APIキー → Redis日次カウンタ（JST 0時リセット）→ Stripe
```

### 5.2 非交渉の設計要件

**(a) 生データレイクは必須。** 指標追加・バグ修正のたびに全期間を再構築する。
EDINETを再度全部叩き直すのは非現実的かつ公的インフラに対して不作法。

**(b) 全ファクトに出所を持たせる。** `source_doc_id` + `source_element_id` は削らない。
監査可能性であり、デバッグ手段であり、競合要件でもある（対象サービスは既にこれを中核訴求）。

**(c) 冪等な取り込み。** 訂正報告書は上書きではなく**追加**し、ビュー側で版を選ぶ。
as-reported を失わないこと（§7の差別化に直結）。

**(d) 名寄せ表をコードに埋めない。** データとして持ちバージョンを付ける。
EDINETタクソノミは毎年改訂される。

**(e) 上場廃止企業を最初から設計に入れる。** 後付けは難しい。`listing_status` を
最初からスキーマに持つ（§2.1）。

### 5.3 規模見積り

| 項目 | 概算 |
|---|---|
| 対象書類数 | 4,600社 × 10年 ×（有報 + 半期/四半期 + 訂正等）≒ 15〜20万書類 |
| 生データ容量 | XBRL ZIP 平均2〜5MB → **300GB〜1TB**（PDF保存で増加） |
| facts行数 | 4,600社 × 10年 × 152項目 × 2(連結/個別) ≒ **1,400万行** |
| 月額インフラ | ストレージ数千円 + Postgres + アプリ ≒ **月1〜3万円**規模 |

### 5.4 初回バックフィルの実務

- 過去10年 ≒ 3,650回の `/documents.json` + 書類本体DL
- **必ずレート制御して数日かけて流す。** 公的インフラに負荷をかけてアクセス制限を
  受けると事業の根が絶たれる
- CSV(type=5)で先に主要10〜20指標の価値を出し、XBRL精査は後追いでよい

## 6. MCP設計（差別化ではなく必須要件）

初版では「少数の高機能ツールが後発の勝ち筋」と書いたが、対象サービスは**既に5ツール構成**で
実現済みだった。したがってこれは差別化ではなく**参入時の最低ライン**である。

### 6.1 バッチ対応を必須にする

```
search_companies(query, filters)
get_company(code)
get_financials(codes[], fields[], periods[], basis)   ← ★複数社×複数指標×複数期を1回で
get_ranking(metric, filters, limit)
get_analysis(code)
get_source(fact_id)                                   ← 出所（docID・要素ID・原本リンク）
```

1社1指標1期ずつ呼ばせるとAIが数十回ツールコールし、レート制限に当たり、遅い。
「10社 × 5指標 × 5期を1コール」で返せれば Free枠100回/日でも実用的な分析が回る。
**UXであり、同時にコスト構造でもある。**

### 6.2 レスポンスはトークン効率で選ぶ

```
悪い: [{"company":"トヨタ自動車","fiscal_year":2025,"field":"net_sales","value":45095325,"unit":"JPY mn"}, ...]
良い: # unit=百万円 basis=JP-GAAP consolidated=true
      code,year,net_sales,operating_income,net_income
      7203,2025,45095325,5352934,4765086
```

同じ情報量でトークンが3〜5分の1になる。単位・会計基準・連結区分はヘッダで1回宣言する。

### 6.3 AIの誤読を防ぐのはサーバー側の責務

レスポンスとツールdescriptionに必ず明示する: 単位 / 連結・単体 / 会計基準 /
実績・予想 / 会計期間（変則決算の注記）/ **訂正の有無**。
ここを曖昧にすると「AIが自信満々に間違う」最悪のUXになる。

### 6.4 接続方式

Remote MCP（Streamable HTTP）が本命。Claude Desktop 向けには `npx mcp-remote` での
ブリッジ手順を提示する（対象サービスと同様）。認証はAPIキー/Bearerで始め、
需要が出たらOAuth 2.1へ。

## 7. 差別化の再評価：埋まっている穴と残る隙

### 7.1 既に埋まっている（差別化にならない）[確]

| 初版で挙げた候補 | 現状 |
|---|---|
| 監査可能性・原本リンク | 中核訴求。1データ点ごとにdocID保持 |
| 有報テキスト・非財務の構造化 | 政策保有株式（銘柄数・簿価）、平均年収・年齢・勤続年数、女性管理職/役員比率、男性育休取得率、GHG(Scope1+2)、主要販売先開示数、セグメント数、関係会社数、役員数 |
| 株価との結合 | PER・PBR・PSR・時価総額・EV・EV/EBITDA・FCF利回り・益回り・配当利回り・配当性向 |
| MCPの少数ツール設計 | 5ツールで実現済み |
| 大量保有報告書 | 大株主検索（5%超大株主から逆引き） |
| 速報性 | 決算カレンダー。決算短信対応 [要検証] |
| 高度な収益性指標 | ROIC、Greenblatt風投下資本利益率（EBITDA版・営業NWC版）まで実装 |
| 英語圏 | `edinetdb.com` が存在 |

**指標カバレッジで勝負するのは消耗戦。**（147→152の数を追う競争に意味はない）

### 7.2 残る隙 [要検証: API仕様書で確認必要]

#### (A) ポイントインタイム（PIT）データ ★最有力

「**その時点で実際に入手可能だった数値のみ**」を返す機能。

- 2020年3月時点のバックテストで、2021年に訂正された数値を使うと**未来情報の混入**になる
- クオンツ・アカデミアではPITでないデータは使えない場合がある
- 実装は重い（`first_reported_at` と全訂正履歴が必要）が、§5.2(c) の設計があれば延長で作れる
- 対象サービスは過去上場826社を持ちサーバイバル・バイアス対策済み = PIT需要のある層を
  既に抱えている。**PIT未対応ならここが最大の隙**

#### (B) 訂正・修正再表示（restatement）の差分追跡

「いつ何がどう訂正されたか」。as-reported vs restated の両建て提示。
プロが金を払う情報で、実装が地味に重く参入されにくい。(A)と基盤を共有する。

#### (C) セマンティック検索 / 埋め込み

指標化は既にされているが、**本文の意味検索**は未確認。
「サプライチェーン分断リスクを新規に記載した企業」「リスク記述が類似する企業」
といったクエリは指標化では出せない。有報テキストの埋め込み + ベクトル検索。

#### (D) プッシュ型配信（Webhook / 差分ストリーム）

現状はプル型API。「この企業の新規提出があったら通知」「訂正が出たら通知」は
モニタリング用途（議決権行使・与信・競合監視）で価値が高い。

#### (E) 未着手ドメイン ★戦略的にはこれが本命

§3の通り、相手の勝ち筋はマルチドメイン化。同じプレイブック
（公的一次情報 → 決定論パース → 構造化 → 無料Web/SEO → API/MCP → 学術リファレンス化）を
**彼らが未着手のドメイン**に適用するのが最も合理的。

医療・医薬（PMDA・審査報告書）/ 特許（J-PlatPat）/ 司法（判例）/ 教育 /
農林水産 / 交通・物流 / 政府統計（e-Stat）/ 入札・調達 など。

### 7.3 やらないほうがよいこと

- 指標数・エンドポイント数での勝負
- 料金の単純な下回り（インフラが安い市場では底なしになる）
- EDINET単体での正面衝突（§3のコスト構造で不利）

## 8. 法務・コンプライアンス

| 論点 | 対応 |
|---|---|
| **元データの権利** | EDINET開示書類は公開情報。EDINET利用規約 / API利用規約に従う。出典表示・加工物である旨の明示・免責。**規約原文を必ず読む** [要検証] |
| **金商法（投資助言・代理業）** | ①スコアはルールベース + ロジック公開 ②売買推奨・目標株価を出さない ③「投資助言・代理業に該当しない」旨を明記。§2.3が実例。**要法務確認** |
| **データの正確性** | 利用規約で保証否認 + 出所リンクで検証可能に |
| **再配布** | 自社データの再配布・API再提供の禁止条項。ただし商用利用は広く許可する方が普及する |
| **TDnet / 各社IR** | EDINETとは別の利用条件。個別確認。スクレイピングの可否と負荷 |
| **特商法・資金決済** | Stripe + 特商法表記 |

## 9. 競合マップ

| 競合 | 強み | 弱み |
|---|---|---|
| **公式EDINET API**（金融庁） | 無料・一次情報・全書類 | 書類配達のみ。横断検索・時系列・名寄せなし |
| **EDINET DB** | 4,646社（過去上場含む）、152指標、MCP 5ツール、原本リンク、学術リファレンス、5ドメイン基盤 | 単一データソース系。PIT/restatement/セマンティック検索は未確認 |
| **J-Quants API**（JPX系） | 株価・売買情報の一次性 | 有報テキスト・詳細財務は薄い |
| **バフェット・コード等** | 個人投資家向けUI | API/AI接続は主眼でない |
| **SPEEDA / QUICK / 日経NEEDS** | 網羅性・品質・サポート | 年数百万円級 |
| **スクレイピング系** | 手軽 | 規約リスク・不安定 |

**空いていた席**（機関投資家向け高額サービスと無料生APIの間の、AIネイティブ・監査可能・
月数千円レンジ）は**対象サービスが既に座っている**。後発は同じ席を奪うより隣に座る。

## 12. 結論

### 技術的な結論

- **作れる。** インフラは月1〜3万円規模で足り、規模も小さい
- **難所は1点**: XBRL名寄せ（会計基準差・企業独自拡張・コンテキスト選別・訂正管理）
- **一級要件は3つ**: 生データレイク / 全ファクトの出所記録 / 上場廃止企業を含むスキーマ。
  最初に入れれば後からやり直せる。入れないと詰む

### 事業としての結論（率直に）

**EDINET領域で正面から同じものを作ることは推奨しない。** 理由は3つ。

1. 初版で挙げた差別化候補（監査可能性・テキスト構造化・株価結合・MCP設計）が
   **すべて既に実装済み**だった。機能面の空白はほぼない
2. 学術リファレンス化（国内主要大学 + 海外大学 + 米連邦政府研究者）は
   **参照が積み上がる複利型の堀**で、機能で追い抜いても埋まらない
3. 相手は5ドメインで基盤を償却するプラットフォームであり、1ドメイン専業は
   **コスト構造で不利**

### 現実的な3つの選択肢

| 選択肢 | 内容 | 向く条件 |
|---|---|---|
| **A. 別ドメインで同じプレイブック** ★推奨 | 医療・特許・司法・統計等の未着手領域に、決定論パース + 無料Web/SEO + API/MCP + 学術リファレンス化を適用 | 「一次情報をAIが検証可能にする」事業そのものをやりたい場合 |
| **B. PIT / restatement で深く刺す** | §7.2(A)(B)。クオンツ・アカデミア・与信向けの高単価ニッチ | 金融ドメインに強い動機がある場合 |
| **C. 作らず、上に乗る** | 対象サービスのAPI/MCPを使い、アプリ層（スクリーナー、IR支援、与信、M&A候補抽出等）で価値を出す | 作りたいのがデータ基盤ではなく**用途**である場合 |

C を選ぶなら、Free枠100回/日で仮説検証まで到達できる。
**「データ基盤を作りたい」のか「分析体験を作りたい」のかで A/B と C が分かれる。**

### 次に決める必要があること

1. **上記 A / B / C のどれか**（最重要）
2. ターゲット顧客（個人開発者 / クオンツ・機関投資家 / 事業会社の企画 / 学術 / 海外）
3. A を選ぶ場合のドメイン選定
4. 技術スタック（言語・DB・ホスティング）
